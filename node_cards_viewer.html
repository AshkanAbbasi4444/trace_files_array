Everything is about the line that just ran: the amber line in the code.

free() wrote 16 bytes hereUnder a card: a library call wrote into this block on this line (a gdb watchpoint caught it)
??Not set yet: whatever bytes were left there
An array: one box per element, its index on top. Amber: the element this line changed. Dark outline: an element it read. ↑i: an int indexing the array right now, from any function that has a pointer to it, in that function's colour (amber if it just moved). A dashed end box is one past the last element. A malloc'd array is a heap card: its slots are ?? until set (calloc's start at 0), a char one shows its letters and the \0 that ends it
Range shading: two indexes of one array compared in a loop or an if (lo <= hi, left < right): the slots between them are still in play (light blue), the ones outside are faded. mid (from (lo + hi) / 2 or lo + (hi - lo) / 2) is bold. A purple bracket: the window between a[i - k] and a[i] on one line. lo > hi: empty range. Turn it off with Shade ranges
A grid: int **grid is a column of row pointers on the left (i→ marks the row in use), each with an arrow to its row; the rows line up with their [j] on top (↑j under the row being indexed). Rows may have different lengths. char ** rows are strings. int grid[2][3] and char board[3][3] on the stack: the same, inside one box
"hello" h e l l o \0A char array: one slot per char and the \0 that ends it, with its text on the line above. char *words[3]: each slot's string is above it, and every pointer slot gets its own arrow. struct pair a[4]: each slot is a little card with its fields
A tree: a struct with left and right (or lchild, rchild) pointers to its own type. Root on top, children below, left to right in in-order. A dashed NULL stub under a missing child. Several trees sit side by side; other blocks follow below. Lists stay in a row
A struct inside a struct: a box of its own inside the card (or the variable's box), with its own fields, highlights and ?? until set. Named like item->pos.x, (*item).pos.x and &item->pos. A struct variable on the stack shows its fields one per line
A doubly linked list (next and prev): cards in next order, next arrows below, prev arrows above; the list line reads 1 ⇄ 2 ⇄ 3 → NULL. A red arrow and a ⚠ note: a node whose prev (or next) doesn't point back, like 0x200's prev doesn't point back to 0x100
head: 1 → 2 → 3 → (back to 1)A circular list: following next comes back to the first node. Its cards are in next order and the last arrow curves back under them to the first card
items head 10 ⇄ 30 → (back to items)A kernel-style list (struct list_head inside each item): arrows land on the item's list field, and hovering one shows container_of(p, struct item, list), the item it's in. A list_head on the stack or a global is the list's head: the circle goes through it. Globals, your file's global and static variables, sit in their own box above the frames
head: 1 → 2 → 3 → 4 → (back to 2) ↻ loop startA loop back into the middle (a "ρ" shape): the last next points to an earlier node. Its arrow curves back to that node, which is marked ↻ loop start; a walk from the head never reaches NULL
r->buf [0] [1] [2] …An array inside a struct (int buf[5]), in a card or a struct variable: slots like any array, with their indexes, ?? until set, highlights, ↑i and the out-of-bounds check. Named r->buf[2], (*r).buf[2], &r->buf[2]. More than 16: a "+N more" box
at 0x…Under every box: the address where it lives (the simple one, or the real one: see View)
printf("*ptr = %d\n", *ptr); → 42Hover a box, a field or an array slot: the printf lines that print its value and its address from the running function, and what they print now. Click it to pin them, with a Copy button per line (Esc lets go)
read-onlyA char * to a string literal: the text it points to lives in read-only memory
Bar on the left of a box: how many hops away it is (own, 1, 2, 3+)
Each function has its own colour; main is always slate

Watchpoint marks

guess: may be wrongmalloc() will hand back one of the freed blocks, but trace.py can't know which one before it runs. It guesses the newest freed block of the right size and watches only that. If the guess is wrong, a write inside malloc() isn't shown
some writes may be missedThe CPU has only 4 hardware watchpoints of 8 bytes each (32 bytes). This call may write more than that (memset on a big struct, calloc, realloc), so writes past those 32 bytes aren't shown

+0…+78 bytes a row, lowest address on the left (little-endian)
